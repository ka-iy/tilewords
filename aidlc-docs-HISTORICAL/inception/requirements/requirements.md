# Requirements Document — Squabble (Cross-Platform Scrabble in Go)

## Intent Analysis Summary

- **User Request**: Build a complete, graphical Scrabble game in Go targeting desktop (Windows/macOS/Linux) and Android mobile, with an Appel-Jacobson (1998) engine, 1–10 AI difficulty levels, multi-dictionary support, and no bluffing.
- **Request Type**: New Project (Greenfield)
- **Scope Estimate**: System-wide — multiple subsystems (game engine, UI, AI, dictionary management, persistence)
- **Complexity Estimate**: Complex — algorithmic game engine, cross-platform graphics, AI difficulty modelling, embedded multi-dictionary support

## Functional Requirements

### FR-01: Cross-Platform Graphical Application
- The game MUST be built using **Ebitengine** (pure Go 2D game engine).
- Target platforms:
  - **Desktop**: Windows, macOS, Linux
  - **Mobile**: Android
  - **Web (WASM)**: Nice to have — not a hard requirement for v1
- The application MUST have a graphical interface including a 15×15 Scrabble board, tile rack, score display, and game controls.
- Board and tile visuals MUST use open-licensed Scrabble-style images (sourced, attributed, and bundled as static assets).

### FR-02: Game Engine — Appel-Jacobson Algorithm (1998)
- The move generation engine MUST implement the algorithm described in:
  > Appel, A. W. & Jacobson, G. J. (1988). "The World's Fastest Scrabble Program." *Communications of the ACM*, 31(5), 572–578.
- The internal word graph data structure MUST be a **GADDAG** (as specified in the paper), which enables efficient left-extension move generation.
- The engine MUST enumerate all valid moves for the current board and rack state.
- The engine MUST score each candidate move correctly (letter values, double/triple letter, double/triple word, bingo bonus).

### FR-03: Dictionary Management
- The following dictionaries MUST be available for selection at game start:
  1. **CSW** — Collins Scrabble Words
  2. **SOWPODS** — (same as CSW for English; treated as a distinct selectable entry)
  3. **OSPD** — Official Scrabble Players Dictionary
  4. **NWL/NASPA** — NASPA Word List (TWL successor)
  5. **OTCWL** — Official Tournament and Club Word List
  6. **All Dictionaries** — Union of all five with duplicate words removed
- Dictionary word lists MUST be **embedded in the binary at compile time** using `go:embed` (no external files required at runtime).
- When the "All Dictionaries" option is selected, duplicate words MUST be eliminated before the GADDAG is constructed.
- Dictionary selection is made once per game session at game start.

### FR-04: No-Bluffing Rule
- Every word placed on the board MUST be validated against the selected dictionary in real time **before** the move is committed.
- Invalid words MUST be rejected and the player prompted to choose a valid word or take another action.
- No penalty is applied for attempting an invalid word — the move is simply disallowed.

### FR-05: AI Computer Player — Difficulty Levels 1–10
- The game offers exactly one AI computer opponent.
- Difficulty is selectable from 1 (weakest) to 10 (strongest) before game start.
- **Level 10**: Always selects the move with the maximum possible score from all valid moves generated by the engine. Ties are broken by preferring moves that open **fewer premium squares** for the opponent (i.e., minimise the opponent's scoring opportunities on their next turn).
- **Level 1**: Selects a move **randomly** from the full set of valid moves (uniform random selection).
- **Levels 2–9**: Linearly interpolated between random and optimal. At level N, the engine:
  1. Ranks all valid moves by score (highest first).
  2. Selects from the top `k` moves, where `k = max(1, total_moves × (1 - (N-1)/9))`. At level 9, k = top ~11% of moves; at level 2, k = top ~89%.
  - This produces a smooth progression from fully random (level 1) to fully optimal (level 10).

### FR-06: Tile Bag
- The standard **100-tile North American English** Scrabble distribution is always used, regardless of dictionary selection.
- Tile counts and point values follow the standard distribution (2 blanks, 9 As, 2 Bs, etc.).
- Tiles are drawn randomly from the bag.

### FR-07: Game Rules — Official Tournament Rules
- **Turn structure**: Draw tiles to replenish to 7; play a word, exchange tiles, or pass.
- **Tile exchange**: A player may exchange any subset of their tiles when there are ≥7 tiles in the bag.
- **Passing**: A player may pass on any turn.
- **End condition**:
  - The game ends when one player has played all tiles and the bag is empty (standard end), OR
  - Six consecutive passes have been made across both players (no progress end).
  - At game end, each player's score is reduced by the sum of their remaining tile values; the emptied-rack player gains those points.
- **Bingo**: Playing all 7 tiles in a single turn awards a 50-point bonus.

### FR-08: Human vs. Computer — One Human Player
- Each game is one human player vs. one AI computer player.
- Human plays first by default (or randomised — TBD in design).
- The AI's rack is hidden by default. A toggle button labelled "Show AI Rack" / "Hide AI Rack" allows the human player to reveal or conceal the AI's tiles at any time during play. When visible, all AI tiles and their letters are shown so the player can verify the AI only plays tiles it legitimately holds.

### FR-09: Undo Move
- The human player may undo their **most recent completed move** (one undo level).
- Undo restores the board, tile rack, bag, and scores to the state before that move.
- The AI's previous move is also undone.
- Undo is NOT available for the AI player's moves independently.
- Undo is only available immediately after the human's move (not across multiple turns without new moves).

### FR-10: Save and Resume
- The human player may save the current game state to a **local file** at any time.
- The saved game can be loaded at the next application launch to continue.
- Save format: structured binary or JSON, stored in the platform's standard app data directory.
- Only one save slot is required for v1.

### FR-11: Game Language
- English only at v1 launch.
- All UI text, tile labels, and in-game messages are in English.

### FR-12: Word Definitions (post-v1)
- During gameplay, the player can view the meaning of each word formed.
- Definitions come from a public-domain / open source with strong coverage of word-game
  vocabulary (Wiktionary via kaikki.org), attributed per its licence (CC BY-SA).
- Definitions are shown in a "Definitions" tab beside the move history, one entry per word,
  and repopulate when a saved game is resumed.
- The feature is optional: if its asset is not built, the game runs without definitions.
- **Implemented by**: Unit 6 `defs` + UI integration. See `construction/defs/` and
  `construction/ui/functional-design/move-history-and-definitions.md`.

### FR-13: Game Modes (post-v1)
- At game start the player selects a game mode. **Classic** uses the standard premium-square
  layout and 100-tile economy; **Interesting** uses an independently-designed pinwheel layout
  and a 110-tile frequency-derived economy.
- A per-mode preview shows the board layout and tile economy before selection.
- The chosen mode is fixed for the game and persisted so a resumed game keeps the same board
  and economy. The designs must not copy any trademarked board (NFR-09).
- **Implemented by**: `engine` game modes + UI selection. See
  `construction/engine/functional-design/game-modes.md`.

### FR-14: Move-History Notation (post-v1)
- The player can choose to display the move history in Scrabble coordinate notation
  (e.g. `8D UNMIX +28`) instead of the plain word list; the choice is persisted per game.
- **Implemented by**: `engine` notation + UI toggle. See
  `construction/engine/functional-design/notation-and-move-records.md`.

### FR-15: Persistent Default Setup Settings (post-v1)
- The New Game Setup screen provides a **"Save these as my defaults"** checkbox, checked by
  default whenever the screen opens.
- When the player starts a game with the box checked, the current setup selections are
  persisted as the player's default settings:
  - dictionary (word list),
  - game mode,
  - AI difficulty level,
  - move-history Scrabble-notation toggle.
- When the setup screen is next opened — on app restart, or on returning to it from the main
  menu to start another game — the saved defaults pre-populate every control, so the player
  can start with their previous choices in a single tap on **Start Game**.
- Persistence MUST be **extensible**: it is defined over a single settings model serialised
  as one document, so any setup option added in the future is saved and restored
  automatically, with no change to the save/load mechanism itself.
- Persisted values are untrusted input on load: unknown or out-of-range values (e.g. a
  dictionary no longer bundled, a difficulty outside 1–10) MUST fall back to the built-in
  default rather than error or crash.
- **Implemented by**: `ui` setup screen + a settings store over Fyne `Preferences`. Detailed
  spec: `inception/requirements/feature-persistent-default-settings.md`; construction design
  to be produced at `construction/ui/functional-design/persistent-default-settings.md`.

> **Note on FR-10 (Save and Resume)**: implemented as a single atomic save slot
> (`savegame.gob`) that persists the full game state including game mode, move history, and
> notation preference, with backward-compatible decoding of older saves. See
> `construction/ui/functional-design/save-and-resume.md`.

## Non-Functional Requirements

### NFR-01: Performance
- Move generation for the AI engine MUST complete within **500 ms** on modern desktop hardware (Intel/AMD 2018+, ARM64) at all difficulty levels.
- The UI MUST maintain a smooth frame rate (≥30 fps) on desktop; ≥30 fps on mid-range Android devices (2020+).
- GADDAG construction from the word list at startup MUST complete within **3 seconds** on target devices.

### NFR-02: Portability
- The entire application MUST be buildable from a single Go source tree using standard Go toolchain commands:
  - Desktop: `go build`
  - Android: `gomobile bind` / `ebitengine` Android build pipeline
  - WASM (optional): `GOOS=js GOARCH=wasm go build`
- No platform-specific native code (C/C++) unless required by the Ebitengine graphics backend (which is acceptable).

### NFR-03: Binary Size
- Embedded dictionaries will be large. The binary MUST use compressed embedding (`go:embed` with pre-compressed word lists decompressed at startup) to keep binary size under **50 MB** on desktop.

### NFR-04: Reliability
- The game MUST recover gracefully from save-file corruption (detect, warn, and offer to start a new game).
- AI move selection MUST never produce an illegal move or crash.

### NFR-05: Usability
- The difficulty level MUST be selectable from the main menu before each game.
- The dictionary MUST be selectable from the main menu before each game.
- The board MUST visually distinguish premium squares (DL, TL, DW, TW, centre star).
- The human player's tile rack MUST support drag-and-drop tile placement onto the board.
- Tile placement MUST support both click-to-select-then-click-to-place and drag-and-drop.

### NFR-06: Open-Licensed Assets
- All graphical assets (board, tile images) MUST be open-licensed (CC0, CC-BY, or equivalent) with attribution documented in a `CREDITS.md` file.

### NFR-09: Hasbro Trademark Compliance
- The game MUST NOT use any Hasbro-trademarked names, branding, or trade dress. Specifically:
  - The word **"Scrabble"** MUST NOT appear in the application name, window title, binary name, app icon, or any in-game UI text. The project name **"Squabble"** is used throughout.
  - The distinctive **Scrabble board colour scheme and layout** (premium square colours, exact board graphic reproduction) MUST be independently designed and MUST NOT reproduce Hasbro's copyrighted board artwork.
  - **Tile design** (font, style, colour) MUST be independently created and MUST NOT copy Hasbro's trademarked tile appearance.
  - The **letter point values** (e.g., A=1, Q=10) are considered facts, not intellectual property, and may be used freely.
  - All marketing copy, `README`, and in-game text MUST describe the game generically (e.g., "a crossword board game") without referencing Hasbro trademarks.
  - The `CREDITS.md` MUST include a disclaimer that the game is an independent work not affiliated with or endorsed by Hasbro, Inc.
- Legal review of asset designs is recommended before public distribution.

### NFR-10: Code Commentary
- All Go source files MUST include meaningful code comments throughout:
  - Every **exported** function, type, constant, and variable MUST have a GoDoc-compliant comment (`// FunctionName ...`).
  - Every **unexported** function or method with non-obvious logic MUST have an explanatory comment describing what it does and why.
  - Every **package** MUST have a `// Package packagename ...` doc comment in at least one file.
  - **Algorithm-critical sections** (GADDAG construction, move generation traversal, AI scoring) MUST include inline comments explaining the algorithm step and its correspondence to the Appel-Jacobson paper (with paper section references where applicable).
  - **Constants and magic numbers** MUST be named (no bare literals) and the named constant MUST have a comment explaining its source or rationale.
  - Comments MUST describe the **why** (intent, constraint, algorithm reference) not just restate the **what** that the code already expresses.

### NFR-07: Testability
- The game engine (GADDAG construction, move generation, scoring) MUST be fully unit-testable without a running UI.
- The AI difficulty logic MUST be unit-testable with a mock move set.
- **PBT Framework**: `rapid` (Go property-based testing library) MUST be used for property-based tests.

### NFR-08: Security
- Game save files MUST be written to the OS-standard app data directory with appropriate file permissions (no world-readable saves).
- Dictionary word list data embedded in the binary is read-only and requires no special access controls.
- Error messages displayed to users MUST NOT expose internal Go stack traces or file paths.
- See Security Extension rules (SECURITY-01 through SECURITY-15) — enforced as blocking constraints throughout the workflow.

## Key Architectural Decisions (From Requirements)

1. **Language**: Go (entire stack — engine, UI, AI, I/O)
2. **UI Framework**: Ebitengine
3. **Engine Data Structure**: GADDAG (Appel-Jacobson 1998)
4. **Dictionary Embedding**: `go:embed` with compressed word lists
5. **Mobile Target**: Android only (iOS deferred)
6. **Platforms**: Windows, macOS, Linux, Android
7. **Dictionary Deduplication**: At GADDAG build time — union word list, sorted and deduplicated before insert
8. **AI Model**: Random-to-optimal linear interpolation by rank percentile
9. **No bluffing**: Pre-move dictionary validation, rejection without penalty
10. **Tile bag**: Always standard 100-tile NA English distribution
11. **Game rules**: Official tournament rules (6-pass end condition)

## Out of Scope (v1)

- iOS support
- Multiplayer (human vs. human, networked or local)
- Non-English dictionaries or tile sets
- Cloud save / account system
- Variant rulesets (e.g., Super Scrabble, Power Tiles)
- Word definitions / dictionary lookup UI
